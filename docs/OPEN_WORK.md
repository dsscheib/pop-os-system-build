| OW-4 | Open / unassigned | `suspend-then-hibernate` sometimes wakes at `HibernateDelaySec` (1h) and stays awake instead of hibernating. systemd checks its wake timer with a zero-timeout poll, which can run just before the timer has expired, so it treats the RTC wake as a manual one ([systemd#38193](https://github.com/systemd/systemd/issues/38193), open; reported mostly on Framework laptops and still present in systemd 261). Seen on the Framework 13 Pop!_OS 24.04 laptop on 26 Nov 2026: the morning run stayed awake for an hour, and the afternoon run, on battery with debug logging, hibernated and resumed with apps open. With the lid closed, logind suspends again and the cycle can repeat without ever hibernating. `rtc_cmos.use_acpi_alarm`, the fix for a similar Framework report, is already on. | Proposed workaround: a systemd-sleep post hook that, when the suspend step of `suspend-then-hibernate` wakes within a few seconds of the deadline, waits until the deadline has passed, so systemd sees a timer wake. Needs a decision, then several hardware cycles. | systemd 255 runs post hooks synchronously before it polls the timer (`src/sleep/sleep.c`), which is what makes the hook possible. Closes when several cycles on the laptop hibernate with the workaround, or when upstream fixes it. |
